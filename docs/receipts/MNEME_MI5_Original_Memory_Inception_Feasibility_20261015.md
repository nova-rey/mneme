The HF Qwen evaluation bundle is the more developed reference path, but it is not a self-contained runnable release at this commit:

- `qwen3_eval/qwen3_moe/evals/run_gsm8k_style_eval.py` imports `style_eval_lib`, which unconditionally imports `long_context.style_track_a` and `long_context.style_traits`. - Core code first tries `descriptor_memory_persona` imports. Some of these are optional because the clone contains flat-file fallbacks (`memory.py`, `attention_patch.py`, and `mlp_conditioning.py`). `runtime.py` also imports `descriptor_memory_persona.runtime`, but its fallback loads `runtime` while the bundle loader is already registering the same root `runtime.py`; the expected `GenerationConfig`/generation helpers are not present elsewhere in the release. This prevents treating the runtime as a self-contained module absent the external workspace package.
- `qwen3_eval/requirements.txt` pins Transformers/PyTorch-era dependencies but the MSI has neither PyTorch nor Transformers installed. The named canonical entry point could not reach model loading: its `--help` import attempt stopped with `ModuleNotFoundError: No module named 'torch'`.

Official Qwen3-4B uses `model_type: qwen3` / `Qwen3ForCausalLM`, so the preferred local family control fails that stock architecture gate. Although a `--no-strict-architecture-check` option exists, using it would be a compatibility override and would not supply the missing runner dependencies.

The baseline `run_gsm8k_vllm_eval.py` only offers `plain` and `prompt`; the intervention runner imports `vllm_port.qwen3_moe_intervention_model`, which is absent. `vllm` is not in the HF requirements file and no vLLM version is pinned in the repository or paper.

**Exact code-to-paper provenance is unresolved.** The inspected release does not establish that this exact commit produced the paper’s reported results. The paper describes its method and Qwen experiments, but no commit or source-tree identity ties those results to `578de36a556cadeb9ea433dee2e153d76e70e0ec`. In the release itself, [`qwen3_eval/README.md` lines 1–7](https://github.com/AndyLiuin/Memory_Inception/blob/578de36a556cadeb9ea433dee2e153d76e70e0ec/qwen3_eval/README.md#L1-L7) labels the HF path a “Collaboration Eval Bundle,” while [`vllm_port/README.md` lines 1–5](https://github.com/AndyLiuin/Memory_Inception/blob/578de36a556cadeb9ea433dee2e153d76e70e0ec/vllm_port/README.md#L1-L5) calls vLLM a working port from the HF reference, and [`vllm_port/integration_plan.md` lines 45–60](https://github.com/AndyLiuin/Memory_Inception/blob/578de36a556cadeb9ea433dee2e153d76e70e0ec/vllm_port/integration_plan.md#L45-L60) lists required attention-path data and an integration plan. No HF Qwen checkpoint, PyTorch, Transformers, or `descriptor_memory_persona` package was found on the MSI. No model download was attempted. In particular, the paper’s 30B checkpoint was not downloaded.

The 4B GGUF is a practical llama.cpp inference artifact, but the upstream code expects a Hugging Face `PreTrainedModel` exposing PyTorch layers, hidden-state outputs, and `q_proj/k_proj/v_proj`, Q/K normalization, and RoPE modules. There is no GGUF loader or llama.cpp bridge in the upstream source. Using the GGUF would require a runtime/attention implementation port, which is outside a stock reproduction. The 30B-A3B paper model, normally BF16 in the supplied runners, is far beyond this laptop’s 6 GiB VRAM and 14 GiB RAM envelope; the source has no documented low-bit/offload recipe that makes that exact setup local-feasible. The 98 GiB root volume is nearly full, so large checkpoint/dependency downloads were not safe or useful.

## What differs from MI1–MI3

These are implementation differences, not explanations proved to have caused the earlier Gemma/Qwen family-control results.

| Component | Upstream source | MI1–MI3 reconstruction | Assessment |
|---|---|---|---|
| Host/runtime | HF Transformers Qwen3-MoE reference; paper’s evaluated Qwen path is customized vLLM. | MI3 used Gemma 4 E4B Q2 GGUF through llama.cpp and native capture/attention code. | **Likely consequential** for compatibility and numeric behavior; no causal comparison was run. |
| Memory contextualization | Helpers accept a wrapper template, one or more templates and descriptor variants; default is full descriptor plus variants, with descriptor-span selection and token-slot concatenation. The style eval constructs target/reference style banks. | MI3 used raw, internal-principles, and private-reasoning-note variants, descriptor-aligned concatenated token slots (411 per bank). | **Possibly consequential** in bank content/context; both use multiple text encodings and preserve token slots. |
| K/V construction | HF forward with hidden states; applies the layer `input_layernorm`, native K/V projections and Q/K normalization; stores canonical pre-RoPE keys; V is projected without a separate value norm in this helper. | Native Gemma capture and Gemma-specific K/V projections and normalization, including Gemma’s value normalization, stored at relative RoPE phase zero. | **Likely consequential** as an architecture-specific mapping difference; not evidence of an MI3 bug. |
| Position/query handling | Qwen helpers inverse-rotate the live query for the memory branch and keep bank keys canonical pre-RoPE. | MI3’s Gemma path captures native query state and applies its own Qwen-independent RoPE alignment in llama.cpp. | **Possibly consequential**, because rotary layouts and normalization are host-specific. |
| Site selection | Source contains a calibration selector based on target/reference alignment and bank/prompt mass, selecting layers plus dense heads or Qwen KV groups and freezing a gain schedule. | MI3 froze 16 Gemma query sites across layers 11, 13, 14 and 23 at gain 0.5. | **Likely consequential**; MI3 was not using the paper’s Qwen-specific calibrated KV-group artifact. |
| Attention mixture | Paper’s Qwen-vLLM implementation uses side-bank K/V and a synthetic single-slot prompt-side score/output approximation; source HF helpers contain several selectable mixture operators. | MI3 native Gemma path used its augmented prompt-plus-bank K/V attention path. | **Likely consequential** operator difference. The implementations are not numerically equivalent. |
| Reproducibility assets | Source has no code license, no complete shared runtime/data tree, and does not pin vLLM or a model revision. | MI1–MI3 preserve model/runtime hashes, banks, selector, and outputs for their own method. | **Unresolved** whether the missing author workspace contains the exact paper-result implementation/configuration. |

The source implementation’s APIs and defaults can be read, but there is no source-only test that proves canonical bank construction or generation: bank construction requires real model forwards and hidden states, and intervention requires a real generation path. The limited source checks above establish syntax and import blockers only.

## Direct answers and next step

1. **Can the original code run on the current local hardware?** Not as released with the available artifacts. The HF path lacks required repository assets and dependencies; the local GGUF is not loadable by it. The paper’s Qwen3-30B-A3B path is not practically supported by the current memory/storage configuration.
2. **Did it actually run?** No. We ran source syntax validation and an import/entry-point preflight only; no model or bank was loaded and no inference occurred.
3. **Did stock canonical memory change behavior?** Unknown. There is no valid stock generation result.
4. **Was any change consistent with hidden guidance?** Unknown; no behavioral outputs exist.
5. **What differs from our implementation?** The host/runtime and architecture; bank construction context; K/V normalization; selector unit/calibration; and attention mixing operator, as itemized above. These differences are not causal findings.
6. **Does Gemma work directly?** No. The code is Qwen3-MoE-specific by its default architecture assertion and operates on HF PyTorch models, not the Gemma Q2 GGUF. A Gemma implementation would require nontrivial adaptation.
7. **Smallest practical next step:** obtain a complete, license-clear author release containing the missing runtime/context/data modules and the actual vLLM intervention plugin, plus its pinned versions/configuration. Then evaluate whether a supported Qwen3-MoE checkpoint and inference precision can run locally without filling the nearly full system disk. Do not port this code to llama.cpp or substitute MI1–MI3 and call it stock.

No MNEME state, SAA, CompactStore, production runtime, or developmental specimen was opened or changed. No paid compute was used. The upstream clone and model remain outside Git.
